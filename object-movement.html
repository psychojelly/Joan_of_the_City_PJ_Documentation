Setup & Operation

Moving Objects

Placing show objects from the panel on the Beam Pro — what can be moved, how a move reaches every device, how a placement is saved, and why shadows do not behave like anything else.

✅

Verified on hardware. Everything described here was tested on a Beam Pro driving XREAL One Pro glasses with a Galaxy Tab S9 alongside, both running the same build. Where something is built but not yet confirmed by a physical button press, it says so rather than being written as working.

Movement · The objects

What can be moved

An object is movable when it carries a TargetModelDisplayCtrl component with its modelTarget wired. There is no tag and no layer — the component is the marker, and everything that moves objects finds them the same way.

The panel deliberately lists only what is currently active, because a list offering objects that are not in the scene yet is a list of things that will appear to do nothing. Objects come and go as { ENABLE } cues fire, so the set changes through the show.

⚠️

ShadowCommunion is a decoy. It carries a movable component but is inactive at every point in the show — measured at seven checkpoints across a full pass. It appears in the greyed inactive list and can never be selected. The shadow you can actually move is ShadowFInal_07132026. Removing the component from ShadowCommunion would end the confusion, but that is a prefab edit.

⚠️

Object names are the wire protocol. Move sync and saved positions both key on gameObject.name, so a rename in the editor silently breaks sync for that object — the only sign is a [DirectorMove] no target named … warning in the log. CommunionBodies_Sound_05/13/2026 is especially fragile: slashes and a date in a key that must match exactly on every device.

Movement · Sharing

Getting a move onto every device

A move made on the panel changes that headset only, until director sync is armed. Then it is fanned out by the cue server and every device applies it.

Sync is off by default, everywhere — including the director build. Sharing a move to every device is something an operator opts into, not a state inherited from which APK happens to be installed. With it off, a move logs move NOT shared — director sync is off rather than quietly doing nothing.

CommandWhat it does
/debug/directorsync 1Arm sharing. Absolute, not a toggle, so a repeat is idempotent and the sender always knows the resulting state.
/debug/directorsync 0Back to local-only.
/joan/move <name> x y z rx ry rz scalePlace an object on every device. Absolute values, never deltas.
/debug/targetsLog what is movable right now, active and inactive, with each transform.

Moves are sent as absolute transforms and repeated three times. The transport is UDP: a dropped delta would leave one device permanently offset with nothing to correct it, whereas a dropped absolute is fixed by the next message, and applying the same absolute twice is a no-op.

📐

Positions travel as localPosition. That is deliberate: each headset has its own tracking origin, so world coordinates are not comparable between devices. It holds while movables have identity-ish parents — give one a rotated or scaled parent and the same nudge will produce a different local offset on each device.

Movement · Saving

Named position sets

Positions live on the cue server, not on the headset that happened to make them, so every device loads the same answer and a set can be kept alongside the cue sheet.

The panel's Save button asks for a name and confirms before overwriting an existing one. Load is a picker of saved sets. Reset asks before putting an object back to its authored position. Each device also keeps a local cache, so a set survives the server being unreachable — and says out loud when it is falling back to it, because believing you loaded the shared set while actually loading a private copy is worse than knowing you are offline.

CommandWhat it does
/positions/save <name>Snapshot every movable to the server under this name.
/positions/load <name>Fetch a named set and apply it.
⚠️

Overwrite protection is best-effort. The dialog checks the name against the set list that device last fetched, but the server does not refuse duplicates — so a set created on another device since then is still overwritten without warning.

Movement · Shadows

Why shadows are different

Shadows are not placed once and left. They are re-placed from a table every time a shadow cue fires — which is why moving one used to look like it worked and then undo itself.

Two separate faults made shadow movement impossible, and fixing either alone would have left it broken:

  1. The movable object was never active. The component sat on ShadowCommunion, which is inactive throughout the show, so the shadow could not be selected at all.
  2. Placements overwrote the move. ShadowPositionRandomizer — misleadingly named, since every instance has low == high and so returns a fixed value — re-applies an authored position on each shadow cue. ObjectMover does the same at VQ2101, the late reprise that repeats the 301 shadow system near the end of the show.

Both now consult a placement store first. Authored values seed that store on first use, so nothing looks different until somebody deliberately pins a change, and the authored positions become the starting point rather than an override that always wins.

Placements are keyed by the placement object's own name, which already encodes the cue — ShadowRandomizer_2101_FrontOfCommunion, ShadowRandomizer_2201_NearJoan1 — so they are cue-scoped without anything having to track which cue is playing.

CommandWhat it does
/shadow/pinRecord where the shadow stands now, against whichever placement fired last. The panel's Save button does this too.
/shadow/save <name>Store the placement set on the server.
/shadow/load <name>Fetch a set; it applies on the next shadow cue, not immediately.
⚠️

A shadow move that is not pinned will revert. That is the design, not a bug — the placement re-applies on the next shadow cue. Verified: moved and unpinned, the shadow returned to its authored spot; pinned, it held, including through the VQ2101 reprise.

🌍

Shadow placements are world-space, unlike every other position here. The existing placement code writes t.position, and converting it to local would move every shadow the moment that parent is not at the origin — a silent change to how the show looks, made while fixing something else. The two stores never touch the same transform.

⚠️

There is only one shadow transform. All the placements drive the same object, so "move the shadow per cue" means moving one shadow to a different stored spot per cue — not several independent shadows. If several were intended, that is a wiring question in the prefab.

Movement · What reaches what

What propagates, and what does not

ActionReaches every device?Needs sync armed?
Object move (/joan/move)Yes — verified simultaneously on Beam Pro and tabletYes
Shadow pinYes — verified, tablet stored the same placementYes
Saved position setOnly when each device loads itNo
Reset to authoredNo — stays on that device—
⚠️

A device must have received a cue through the cue server before it can share anything. That is when it learns the server's address, via the announcement that rides with scheduled cues. Firing cues straight at a device bypasses it. In a real show cues always come from the server so this resolves itself, but on a freshly launched device the first pin reports pin not shared — no cue server known yet.

Movement · Setup

What the cue server has to be

Saving and loading positions is a call from the headset straight to the cue server over HTTP. The controller page is not involved — it cannot cause or fix a problem here.

That means the machine answering on port 8765 has to be a cue server that knows these routes. There are two things that can answer on that port, and they are not equivalent:

Running as the cue serverPositions save & loadDirector moves & shadow pins reach every device
python server.py on a PCYesYes
The Android cue app in Operator modeOnly from the parity build onwardOnly from the parity build onward
🚑

404 on Save or Load? The server is answering but does not know the route — it predates the position endpoints. Pull and restart it:

cd joan-cue-controller-android && git pull then restart python pc-server/server.py.

To confirm which you have, ask it directly: curl http://<server-ip>:8765/positions. A current server answers {"sets": [...]}. A stale one 404s. So does the Android app's built-in server — but its /debug/events still answers, which distinguishes it from a server that is not running at all.

📋

The messages you get on failure are deliberate, not breakage. "Saved to this device only… no other device can see them" means the positions were written locally as ObjectTransforms.json rather than discarded, and "No sets to offer: cue server unreachable" means the picker refused to show a list it could not verify. Both are the fallbacks doing their job and saying so.

⚠️

Fire one cue through the server before saving on a freshly launched device. A device learns the server's address from the announcement that rides with scheduled cues. Until then a save reports "no cue server known yet". Firing cues straight at a device bypasses this — it matters most on an isolated test rig.

Movement · Traps

Traps worth knowing

🕳️

A success message is not proof. extOSC's OSCTransmitter.Send begins if (!_transmitterBackend.IsAvailable) return; and the socket only opens once Start() has called Connect(). Creating the transmitter and sending in the same frame therefore sends nothing — while the calling code happily logs that it did. This cost an hour to find, and it affected both broadcast paths. Both now call Connect() explicitly and check IsAvailable before claiming anything. If you add another broadcast, do the same.

🕳️

Scale sync flattens non-uniform scale. The wire carries one scale value and the receiver applies it uniformly, while save/load preserves the full vector. Every movable is uniform today, so it does not bite — but an object authored with a non-uniform scale would silently lose it the moment a director touched it.

🕳️

The rotation slider is yaw-only and destructive. It writes a whole new vector with X and Z hard-zeroed, so touching it flattens any tilt — locally first, then on every device. All objects are yaw-only today.

🧪

Not yet confirmed by a button press. Everything above was driven by sending OSC. The panel's own send path — BroadcastSelectedTransform, fired by nudging on the Beam Pro — has not been exercised by hand. Nudge an object with sync armed and confirm the tablet follows; that closes the last untested step.
