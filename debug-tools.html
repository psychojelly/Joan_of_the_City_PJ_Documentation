Setup & Operation

Debug & Optimization Tools

A second, instrumented build of the show — and the controls that come with it — for answering two questions that are otherwise guesswork: did every headset get that cue, and what is costing the frame rate.

✅

Measured, not estimated. Every figure on this page came off a Beam Pro driving XREAL One Pro glasses, in stereo, during a repeated 37-cue rehearsal. Where a number was later found to be wrong it has been corrected rather than quietly kept — see Traps.

Debug · The build

The debug build

The show build and the debug build are the same show. The debug build adds a panel on the phone screen, a richer heartbeat back to the cue server, and a set of live render toggles. Nothing it adds is on the audience's side of the glasses.

It installs as com.joanofthecity.tester, so it sits alongside the production builds rather than replacing them — see Builds & Downloads.

⚠️

The debug build boots with post-processing already OFF. The bottom button on the phone panel reads Post FX: OFF at startup. If you measure in that state and call it the baseline, you are measuring the optimised case against itself. Press it until it reads Post FX: ON before taking any baseline reading.

The on-device panel

Tapping DEBUG on the Beam Pro screen opens the panel. It shows, top to bottom:

  • Performance — median and worst frame time in ms, frame rate, active renderers / materials / lights, particle and VFX counts, RAM, and render scale.
  • Current cue — position in the list and the cue id.
  • Snap · Rec · STOP ALL — a still, a screen recording, and the panic button.
  • Prev · Next · FIRE — drive this one headset by hand. It desyncs it from the show, which is the point when you are testing one device.
  • Post FX — cycles ON → OFF → + shadows OFF → + sky OFF.
📐

Frame time in milliseconds, not fps. The panel leads with ms because fps hides the size of a change: 11→15 fps looks like “+4” but is a 24 ms saving, while the same +4 at 55→59 fps is 1.2 ms. When comparing two configurations, compare the ms.

Debug · Cues

Did every headset get the cue?

Each device acknowledges every cue it accepts. The cue server records what it expects, and anything unacknowledged after a grace period is reported as a drop — visible in the controller's debug log, with a “dropped only” filter so it isn't lost in the heartbeat traffic.

This is how the roster stays honest: a headset that has gone to sleep, dropped off the WiFi, or crashed produces silence, and silence is indistinguishable from a working show until something asks the question.

📊

Current status: no drops. Across 429 cues in testing — including a 63-minute continuous soak of 244 cues — no device ever failed to acknowledge one. Memory held between 709 and 712 MB with no upward trend, and nothing crashed.

Clock and time-since-last-cue

The controller toolbar carries a wall clock and a counter showing how long since a cue last fired anywhere — this page, a second operator's browser, or QLab. It turns amber past two minutes and red past five. A stalled show and a quiet passage look identical until you can see the gap growing.

What actually costs the frame rate

Measured across a full 37-cue rehearsal with cues 15 seconds apart, so the figures include accumulation — cues stack during a real run and nothing releases them, which makes a rehearsal roughly twice as heavy as any single cue tested alone. Each row includes the ones above it.

ConfigurationControlMedianfpsWorst
As shipped—67.3 ms15123.3 ms
+ bloom off/debug/bloom 033.6 ms30123.4 ms
+ all post off/debug/postfx 127.3 ms3767.7 ms
+ voxel avatar off/debug/voxels 018.2 ms5562.7 ms
+ communion bodies off/debug/vfxlimit 016.8 ms6020.2 ms

Three findings are worth carrying into art decisions:

  • Bloom alone is half the problem. Turning off one effect takes the show from 15 to 30 fps. The rest of the post stack is worth a further 6 ms, and that cost is the off-screen render round-trip rather than the effects themselves.
  • Particle count is not the driver. Correlation across the whole rehearsal was −0.17: a moment with 9,573 particles ran at 54 fps while one with 5,984 ran at 19. The cost is the number of VFX output contexts being drawn — 13 communion bodies × 4 outputs — not the number of particles.
  • The voxel avatar is a per-instance vertex cost. Not its shadow pass (0.1 ms) and not fill rate (size makes no difference). Drawing each voxel as a camera-facing quad instead of a cube saves 15.2 ms — 31 → 58 fps — at full density. The trade is that lighting flattens, since a quad has no real surface direction.
🎯

The configuration worth testing for the show keeps the art rather than deleting it: /debug/bloom 0, /debug/voxelquad 1, and /debug/vfxlimit swept downward from 13 to find where it breaks — rather than turning whole systems off.

Debug · Audio

Per-cue audio reactivity

The reactive intensity used to be reachable only from the Unity inspector, which meant judging a value took a guess, a build, and putting the headset back on — so in practice the numbers were set once and never revisited. The controller now has sliders for it, live.

  • Intensity is relative to the authored value: 100% is exactly what the artists set, 50% halves it, 250% is two and a half times.
  • Gate (low) raises the bottom of the analysed range, gating out quiet passages.
  • Ceiling lowers the top, so the effect saturates sooner.
  • 📌 Pin to current cue remembers the value against whatever cue last fired. It is re-applied automatically the next time that cue runs, and cues without a pinned value go back to as-authored, so one cue's setting cannot leak into the next.

Where the values are kept

On the cue server, in audio-presets.json — not on the headset, and never in the cue sheet. The cue sheet is the show's shared score, fetched from a repository and read by every device; nothing here writes to it.

Server-side means a value found on one headset applies to all of them, survives the app closing, and is applied whether the show is driven from the web page or from QLab. Export downloads the file to pass to someone else; Import loads theirs.

🎚️

The preset is sent to the device immediately before the cue, so the effect is already correct on the frame the cue lands rather than snapping a moment later. Pinning a cue at 100% deletes its entry rather than storing it — 100% is the authored value, and storing it would freeze that cue to today's number and ignore any later change from the art side.

Debug · QLab

Driving the show from QLab

The cue server listens for QLab on port 53000, so QLab can drive the headsets without replacing anything. It runs alongside the existing controller rather than instead of it.

Any of these fire cue B_201:

/joan/cue "B_201"
/joan/cue/B_201
/audio/cue "B_201"

Targets come from devices.txt, or from recent heartbeats when that file is absent. If no devices are known the bridge refuses to fire rather than sending cues into the void, so a silent room is reported instead of being mistaken for a working one.

💻

QLab 5 is macOS only (Big Sur or later). Network cues — the ones needed here — are in the free tier. There is no Windows or iPad version that can send them.

Debug · Traps

Traps worth knowing

Each of these produced a wrong answer at least once. They are recorded because none of them announce themselves.

The glasses can be in 2D mode without saying so

At 3840×1080 @ 60 Hz the glasses are in stereo. At 1920×1080 @ 90 Hz they are showing the same flat image to both eyes — which looks like “two screens side by side”. There is no on-screen warning. An entire round of measurements was invalidated by this before anyone noticed; check the mode before trusting a reading.

Old builds ignore the debug controls silently

The /debug/* control addresses exist only in the instrumented build. A production build discards an address it never bound, without an error — so the sliders would move, the page would report “sent”, and nothing would happen. The controller now detects this from the heartbeat and greys the affected controls out. Presets can still be edited and exported while pointed at a production build.

Build Settings is stale

The project's Build Settings scene list has only one enabled entry, Assets/_DL/beepTest.unity, and that file no longer exists; two other listed scenes are missing too. Builds name the scene explicitly instead — the show is Assets/Scenes/MainScene.unity. The dangerous version of this bug is a stale entry pointing at a scene that still exists, where the build succeeds and quietly ships the wrong one.

Frame times snap to the refresh rate

Vsync is on, so frame times quantise to multiples of the refresh interval — 16.7, 33.3, 50.0, 66.7 ms at 60 Hz. A saving that doesn't cross one of those boundaries is real but invisible. This is also the answer to the “tearing” seen in the glasses: it is judder and reprojection from low frame rate, not tearing. The tell is that world-locked content jitters while the head-locked HUD does not.
